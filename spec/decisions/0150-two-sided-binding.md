# 0150 — A pipeline names an engine and the machine's own configuration defines what it runs

**Status:** accepted 2026-09-18
**Decides:** `derive.bind.refusal.unbound-engine`, `derive.bind.refusal.command-in-a-manifest`

## Context

An `exec` engine runs a binary on this machine with an argument array the operator wrote, a
cleared environment plus an explicit allowlist, and unit data flowing into its arguments. A
`fetch` engine opens sockets to hosts an allowlist names. Both are command authority over the
machine the store sits on.

Pipeline manifests do not come from that machine. A manifest is authored in a shared
repository, handed down by a control plane, copied from an example, or generated by an agent
composing a pipeline from a description. All four are legitimate ways to get a manifest, and
none of them is the party that owns the host. If the command lived in the manifest, authoring
a manifest would be command execution, and every path by which a manifest arrives would become
a path by which arbitrary argv reaches a shell-less spawn with the operator's environment
allowlist behind it.

The other half of the question is where the engine *name* lives. The name is a request, not an
authority, so it could sit in either the manifest or the build context the caller constructs.
But a build context is assembled by every caller — the scheduler, a one-shot run, a test
harness — and a context missing an optional field constructs successfully. An engine name that
could be absent from a context would give a caller a pipeline whose derive step silently does
nothing, with the manifest still reading as configured.

## Decision

A `[[pipeline]]` names an engine in `[pipeline.source.config]`. A `[derive.<name>]` block at
the top level of the machine's own `contextful.toml` states what that name runs: the argv
chain or the host list, the environment allowlist, the content pins and the bounds. A manifest
arriving from elsewhere requests an engine and introduces no command.

A pipeline naming an engine with no matching `[derive.<name>]` block raises
`DeriveEngineUnbound`, naming the pipeline, the engine, the file to edit and every engine the
machine has bound. A `command`, `preprocess`, `env` or `allow_hosts` key written inside
`[pipeline.source.config]` raises `DeriveCommandInManifest`.

## Options considered

| Option | What it buys | What it costs |
| --- | --- | --- |
| **Name in the manifest, definition in the machine's configuration** *(chosen)* | Command authority stays with the party that owns the host; a misconfiguration fails loudly with the file to edit and the bound engines listed | An operator cannot ship a self-contained pipeline — a manifest and a machine-local binding both have to be in place, and the manifest half is inert on an unprepared machine |
| Carrying the command in the pipeline manifest | One artifact; a pipeline is portable and runs anywhere unchanged | Lost on who may introduce a command: it hands argv execution, environment allowlisting and host reach to whoever authors a manifest, including a control plane and an agent |
| Putting the engine name in the build context rather than the source config | Keeps the manifest purely declarative | Lost on failing open: a caller constructing a bare context silently gets a pipeline whose derive step has vanished, with the manifest still reading as configured |
| Manifest command plus an operator allowlist of permitted commands | Portability with a check | Lost on the same criterion as the first: the allowlist is a second parser over argv that has to anticipate every shape a manifest can spell, and a near-match is an execution |
| Signed manifests carrying commands | Authority is explicit and verifiable | Lost on effort and scope: it introduces a signing and key-distribution surface for one configuration key, and the operator still ends up naming trusted signers on the machine |

## Criteria

1. **Whether a manifest arriving from a control plane, a shared repository or an agent can
   introduce a command** — the authority question.
2. **Whether a misconfiguration fails open** — whether a missing value produces a pipeline
   that reads as configured and does nothing.
3. **Portability of a pipeline definition** — how much a deployment writes to run someone
   else's pipeline.
4. **Quality of the refusal** — whether the message names the file to edit and what is already
   bound.

Criteria 1 and 2 decided this together, and they cut in the same direction against different
candidates: the first eliminates every option that puts argv in the manifest, the second
eliminates the one option that moves the name out of it. Portability is real and is the cost
this pays; it lost because a portable pipeline that executes the author's commands is not a
weaker version of the same thing, it is a different security posture.

## Consequences

A pipeline is not self-contained. Running someone else's derive pipeline takes two steps: the
manifest, and a `[derive.<name>]` block written on this machine. An example repository can
ship the manifest and cannot ship the working system. That is the cost accepted.

What gets easier: an operator reads one file — the machine's own configuration — to see every
command the machine will run and every host it will reach, with no manifest to audit. Swapping
an engine implementation across every pipeline that names it is one block edit.

What is now expensive to reverse: refusing manifest-side command keys is a compatibility
boundary. Manifests in circulation are written without them, and permitting them later would
make previously-refused configurations execute.

## Revisit triggers

- A manifest transport arrives with a verifiable authorship claim the machine can check
  against an operator-named signer list.
- The set of `[derive.<name>]` blocks a typical deployment maintains grows large enough that
  operators keep the machine configuration generated rather than written, which changes which
  party is authoring it.
